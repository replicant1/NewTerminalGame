# WI-1: Project scaffold and the layer guard

Risk: MEDIUM
The plan's floor, not raised: a wrong guard would be expensive to unpick once everything is built on it, but nothing here opens a window, touches game behaviour, or reaches the user's desktop.

Lane A, Dev A. Branch `r8/wi-1-scaffold`, cut from `main` at `8bc9496`. Not stacked.

**What it adds:** `requirements.txt`, `pyproject.toml` (the pytest configuration and the layer declaration), a root `conftest.py`, the README sections on setting up, running the tests and the layers, the four empty layer packages under `terminal_game/`, and three modules in `tools/`:

- `tools/runtime_pin.py`: is this CPython 3.14 at `/opt/homebrew/bin/python3.14` with Tk 9? It answers that and words the refusal. It stays parsable by Python 3.9 so that a 3.9 venv gets the message.
- `tools/pytest_guards.py`: the pytest plugin, loaded by `conftest.py`. It refuses a wrong interpreter at start-up, deselects `desktop` tests unless `-m` names `desktop`, and wraps `_tkinter.create` (with `wantTk` true) and `tkinter.Tk.loadtk` so that asking for a window outside a desktop test fails before the window exists.
- `tools/layer_check.py`: an AST scan of every module under `terminal_game/` against the §1.4 rule, driven by the `[tool.terminal_game.layers]` table.

**For lanes B and C:** after this lands, merge `main` before you ask for verification. You will get `terminal_game/__init__.py` and `terminal_game/<layer>/__init__.py`. If you created the same files, that is an add/add conflict: keep either docstring. From then on, the default suite runs the layer check over your modules. A test that opens a window, or that launches the program as a subprocess, needs `@pytest.mark.desktop`.

### What the guards cannot see (stated, not claimed)

- **A window opened by a subprocess** that an unmarked test launches. The guard lives inside the pytest process. I weighed injecting a `sitecustomize.py` into child processes and rejected it: Homebrew's Python already ships its own `sitecustomize.py` (`/opt/homebrew/Cellar/python@3.14/3.14.7/…/lib/python3.14/sitecustomize.py`, measured), and shadowing it is fragile. The README and the plugin's docstring both say that a test launching the program must carry `desktop`. WI-3 and WI-13 are the lanes this affects.
- **`package require Tk` evaluated inside a bare Tcl interpreter.** It is not intercepted.
- **"A working Tk 9"** here means that `tkinter` imports, reports Tk 9, and builds a Tcl 9 interpreter. Tk itself is not initialised, because that creates a window. Whether Tk draws is a question for the desktop tests.
- **On the real tree today, each layer holds only its `__init__.py`.** C4's count of 1 per layer is real, but it counts docstring-only modules until B and C land code. WI-13/C10 re-checks with the finished tree.
